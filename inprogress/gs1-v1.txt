Abstract

   This document describes a Uniform Resource Name (URN) namespace for
   Global Standards 1 (GS1). The namespace provides stable, unique, and
   persistent identifiers for GS1 identification keys, GS1 semantic
   artefacts, and GS1 standards and their components. The namespace
   includes three coordinated branches: an identification branch based
   on GS1 Application Identifiers (AIs), a semantic dictionary branch
   rooted at 'urn:gs1:gdd:', and a standards branch rooted at
   'urn:gs1:std:'. This document registers the formal URN namespace
   'gs1', defines its syntax, provides illustrative examples, and
   includes informative constraints to preserve important GS1
   operational realities without overloading the core ABNF.

1. Introduction

   Global Standards 1 (GS1) is an international standards organisation
   that develops and maintains standards for identification, data
   capture, data sharing, and interoperability across supply chains,
   healthcare, retail, logistics, and digital ecosystems.

   GS1 standards include globally recognised identification keys such as
   the Global Trade Item Number (GTIN), Global Location Number (GLN),
   and Serial Shipping Container Code (SSCC). GS1 also maintains
   semantic artefacts and standards that define business information
   elements, business data types, code lists, and standard clauses used
   across multiple industries.

   This document registers the formal URN namespace 'gs1' in order to
   provide stable, globally unique, and persistent identifiers across
   these domains. The design intentionally separates three categories of
   identified things:

   o  GS1 identification keys and related element strings;
   o  GS1 semantic dictionary artefacts;
   o  GS1 standards and their components.

   For readability, the following informal forms illustrate the three
   categories. The authoritative grammar is contained in Section 2 so
   that the namespace registration template can stand alone.

      1. Identification branch:

         urn:gs1:<ai>:<value>
         urn:gs1:<ai>:<value>:<ai>:<value>

      2. Semantic dictionary branch:

         urn:gs1:gdd:bie:<ref>
         urn:gs1:gdd:bdt:<type>
         urn:gs1:gdd:cl:<list>[:<value>]

      3. Standards branch:

         urn:gs1:std:<standard>
         urn:gs1:std:<standard>:<version>
         urn:gs1:std:<standard>:<version>:<clause>

   The document is intentionally minimalist in scope. It focuses on URN
   namespace registration, syntax, examples, and validation. Resolver
   behaviour and OpenAPI details are retained as informative appendices.

   Syntactic structure:
      The following ABNF grammar defines the namespace-specific string
      syntax for the 'gs1' namespace. This grammar is included directly
      in the registration template so that the registration can be
      reviewed independently of publication of this document as an RFC.

      gs1-urn            = urn ":" gs1 ":" ( id-branch / gdd-branch /
                            std-branch )

      urn                = "urn"
      gs1                = "gs1"

      id-branch          = ai ":" value *( ":" ai ":" value )

      gdd-branch         = "gdd" ":" ( bie-branch / bdt-branch /
                            cl-branch )
      bie-branch         = "bie" ":" bie-ref
      bdt-branch         = "bdt" ":" datatype
      cl-branch          = "cl" ":" codelist [ ":" code ]

      std-branch         = "std" ":" std-id
                            [ ":" version [ ":" clause ] ]

      ai                 = 2*4DIGIT
      value              = 1*( ALPHA / DIGIT / "-" / "_" / "." )

      bie-ref            = 1*( ALPHA / DIGIT / "." )
      datatype           = 1*( ALPHA / DIGIT )
      codelist           = 1*( ALPHA / DIGIT )
      code               = 1*( ALPHA / DIGIT / "_" )

      std-id             = 1*( ALPHA / DIGIT / "-" )
      version            = 1*DIGIT "." 1*DIGIT *( "." 1*DIGIT )
      clause             = 1*DIGIT *( "." 1*DIGIT )

      ALPHA              = %x41-5A / %x61-7A
      DIGIT              = %x30-39

   Identifier attribution semantics:
      The meaning of a GS1 URN is determined by the namespace branch
      under which it is assigned and by the GS1 specification, registry,
      publication, or standards artefact governing that branch.

      A URN in the identification branch identifies a structured
      collection of GS1 Application Identifier assertions. Each
      <ai>:<value> pair represents an assertion whose meaning is defined
      by the corresponding GS1 Application Identifier specification and
      related GS1 specifications.

      For example:

         urn:gs1:01:09506000134352:17:250101

      represents a collection containing:
         AI 01 = Global Trade Item Number (GTIN)
         AI 17 = Expiration Date

      A URN in the semantic dictionary branch identifies a specific
      semantic artefact governed by GS1 semantic standards, registries,
      or specifications. Examples include Business Information Elements,
      Business Data Types, Code Lists, and Code Values.

      A URN in the standards branch identifies a GS1 standard, version,
      or clause. The meaning of the identified resource is defined by
      the referenced GS1 publication.

      For every assigned GS1 URN there SHALL exist an authoritative
      GS1-managed specification, registry, publication, or standards
      artefact that defines the meaning of the identified resource.
      Assignment of a GS1 URN without an authoritative attribution
      source is outside the scope of this namespace registration.

   Identifier uniqueness considerations:
      Identifier uniqueness is guaranteed through GS1 governance.
      Identification-key values are governed by GS1 allocation rules,
      including GS1 Company Prefix governance where applicable. Semantic
      artefacts and standards references are assigned under GS1-managed
      governance processes.

   Identifier persistence considerations:
      Identifiers are never reassigned. Deprecation, withdrawal,
      replacement of standards, migration of semantic infrastructure,
      replacement of resolver technologies, or changes to publication
      formats SHALL NOT invalidate an assigned GS1 URN. The identifier
      remains valid indefinitely, even where the identified resource
      becomes obsolete or superseded.

   Process of identifier assignment:
      Names are granted through GS1 processes. Depending on the branch,
      assignment is managed by GS1 Global Office, GS1 Member
      Organisations, or relevant GS1 semantic or standards governance
      processes.

   Process of identifier resolution:
      Resolution is optional. URN validity is independent of the
      existence of any resolver service. Resolver services provide a
      convenience mechanism for obtaining representations associated
      with a URN. GS1-authorised resolvers MAY provide authoritative
      representations.

      Illustrative example:

         https://resolver.gs1.org/resolve/{urn}

      The URI above illustrates one possible resolver binding. This
      namespace registration neither requires nor asserts deployment of
      a resolver at that URI. Appendix D and Appendix E describe
      informative resolver behaviour and an informative resolver
      interface only; they do not form part of lexical equivalence or
      namespace validity.

   Rules for lexical equivalence:
      The literals 'urn', 'gs1', 'gdd', 'bie', 'bdt', 'cl' and 'std' are
      case-insensitive. All assigned-value components are case-sensitive
      unless explicitly defined otherwise by GS1 governance. No Unicode
      normalisation, percent-decoding, case folding, or semantic
      interpretation is performed when determining lexical equivalence.
      Lexical equivalence is determined using RFC 8141 rules combined
      with the namespace-specific rules defined here.

      No GS1 URN is lexically equivalent to any EPC URN. Mappings
      defined between EPC URNs and GS1 URNs do not create lexical
      equivalence between identifiers.

   Conformance with URN syntax:
      All GS1 URNs conform to RFC 8141 and the specific ABNF grammar
      contained in this registration template.

   Validation mechanism:
      Syntax validation may be performed using the ABNF in this template
      and the regular expressions in Appendix B. Additional branch-
      specific semantic validation should be performed using the
      informative constraints in Appendix F.

   Scope:
      The namespace is global, covering GS1 identifiers, semantic
      artefacts, and standards references maintained or governed by GS1.

3. Namespace Considerations

   The 'gs1' namespace is required to provide stable identifiers for GS1
   artefacts across registries, implementations, APIs, and
   documentation. It enables persistent referencing, deduplication,
   caching, standards citation, semantic linkage, and long-lived
   references in publications and knowledge graphs.

   The namespace design deliberately separates identifiers, semantic
   artefacts, and standards references because these categories have
   different governance and syntactic needs. This reduces ambiguity and
   supports simpler validation and resolution.

   The 'urn:gs1:gdd:' branch is preserved as a legacy-compatible
   semantic namespace. It identifies GS1-governed semantic artefacts
   independently of any particular implementation platform and remains
   valid even if the underlying semantic infrastructure evolves.

3.1. Relationship to RFC 5134

   The GS1 URN namespace defined in this document does not replace,
   deprecate, or supersede the EPC URN namespace defined by RFC 5134.

   The two namespaces serve complementary purposes within the GS1
   standards ecosystem.

   The EPC namespace is specifically designed to support Electronic
   Product Code (EPC) identification schemes and related EPC
   architectures. The GS1 namespace defined in this document provides a
   broader identifier framework covering:

   o  GS1 identification keys and Application Identifiers;
   o  GS1 semantic artefacts;
   o  GS1 standards and standards components;
   o  future GS1-governed identifier classes.

   The GS1 namespace therefore addresses categories of resources that
   are outside the scope of the EPC namespace while preserving
   compatibility with existing EPC deployments.

   Implementations MAY support mappings between EPC URNs and GS1 URNs
   where such mappings are defined by GS1 standards or implementation
   guidance.

   For example:

      urn:epc:id:sgtin:0950600.134352.9999

   may be represented as:

      urn:gs1:01:09506000134352:21:9999

   where the GTIN component is represented using Application Identifier
   01 and the serial component is represented using Application
   Identifier 21.

   The existence of such mappings does not imply lexical equivalence
   between the namespaces. The existence of such mappings also does not
   imply semantic equivalence unless explicitly defined by a GS1
   standard. Each namespace retains its own syntax, governance model,
   and resolution semantics.

   The GS1 namespace is intended to complement the EPC namespace by
   providing a consistent URN framework for the wider set of GS1-managed
   identifiers, semantic resources, and standards references. Additional
   illustrative mappings and mapping guidance are provided in Appendix G
   (EPC <-> GS1 Mapping).

4. Security Considerations

   GS1 URNs contain structured components that are intended to be parsed
   by applications. However, the namespace does not define operations
   that may be invoked solely through possession of a URN. Consequently,
   this registration introduces no namespace-specific security
   considerations beyond those generally applicable to URNs and any
   associated resolver infrastructure.

   Use of non-authoritative resolvers may yield incorrect or outdated
   results. Resolver services should therefore use HTTPS to provide
   confidentiality and integrity, and clients should prefer
   GS1-authorised resolver services where semantic correctness matters.

   Applications that dereference GS1 URNs should consider normal
   security issues for HTTP services, including spoofing, stale data,
   replay, and representation tampering.

   Intellectual property rights associated with identified artefacts are
   outside the scope of this registration.

Appendix A. ABNF Commentary

   The authoritative ABNF grammar for the 'gs1' namespace is contained
   in Section 2 so that the namespace registration template can stand
   alone independently of publication of this document as an RFC. This
   appendix is retained to explain grammar design choices.

   The grammar is intentionally a syntactic envelope. GS1 Application
   Identifier-specific semantics, value lengths, character repertoires,
   and cardinality rules are applied by GS1 semantic validation as
   described in Appendix F.

   The standards branch requires a version before a clause. This removes
   ambiguity between a version and a clause reference.

Appendix B. Regular Expressions

   Identification branch:

      ^[Uu][Rr][Nn]:[Gg][Ss]1:[0-9]{2,4}:[A-Za-z0-9._-]+(:[0-9]{2,4}:[A-Za-z0-9._-]+)*$

   Semantic dictionary branch:

      ^[Uu][Rr][Nn]:[Gg][Ss]1:[Gg][Dd][Dd]:(?:[Bb][Ii][Ee]:[A-Za-z0-9.]+|[Bb][Dd][Tt]:[A-Za-z0-9]+|[Cc][Ll]:[A-Za-z0-9]+(?::[A-Za-z0-9_]+)?)$

   Standards branch:

      ^[Uu][Rr][Nn]:[Gg][Ss]1:[Ss][Tt][Dd]:[A-Za-z0-9-]+(?::[0-9]+\.[0-9]+(?:\.[0-9]+)*(?::[0-9]+(?:\.[0-9]+)*)?)?$

Appendix D. Resolver Behaviour

   Resolver behaviour is informative and not required for URN validity.
   GS1-authorised resolvers should support representation negotiation
   while keeping URNs themselves stable and version-independent where
   appropriate.

   Recommended representations:
      * text/html
      * application/pdf
      * application/xml
      * text/markdown
      * application/ld+json

   For standards references, clause-level resolution should return the
   addressed standard or clause in the requested representation when
   available.

   For semantic artefacts, version-specific representations may be
   negotiated using Accept parameters or query parameters while keeping
   the URN itself version-independent.

Appendix F. GS1 Application Identifier Constraints

   This appendix is informative. The AI values shown in this appendix
   correspond to the <ai> production in the ABNF grammar in Section 2.
   For each listed <ai>, the corresponding <value> component is
   interpreted according to the referenced GS1 Application Identifier
   definition and related GS1 specifications.

   +------+----------------------+----------------------+----------------------+
   |  AI  | Meaning              | Character set        | Length / form        |
   +------+----------------------+----------------------+----------------------+
   | 00   | SSCC                 | numeric              | exactly 18 digits    |
   | 01   | GTIN                 | numeric              | exactly 14 digits    |
   | 10   | batch or lot         | GS1-defined alpha    | variable             |
   | 17   | expiration date      | numeric              | YYMMDD               |
   | 21   | serial number        | GS1-defined alpha    | variable             |
   | 253  | GDTI                 | GS1-defined          | per GS1 definition   |
   | 401  | GINC                 | GS1-defined          | per GS1 definition   |
   | 402  | GSIN                 | numeric              | exactly 17 digits    |
   | 414  | GLN                  | numeric              | exactly 13 digits    |
   | 8003 | GRAI                 | GS1-defined          | per GS1 definition   |
   | 8004 | GIAI                 | GS1-defined alpha    | per GS1 definition   |
   +------+----------------------+----------------------+----------------------+

   Fixed-length numeric values are represented in canonical form,
   including leading zeroes where necessary to satisfy the stated
   length.

Appendix G. EPC <-> GS1 Mapping

   This appendix is informative and is provided to illustrate
   interoperability between the namespaces described in Section 3.1. The
   mappings shown herein do not establish semantic equivalence or
   lexical equivalence between the EPC and GS1 namespaces and do not
   alter the independent governance or syntax rules applicable to either
   namespace.

      urn:epc:id:sgtin:0950600.134352.9999
      ->
      urn:gs1:01:09506000134352:21:9999

   Informative mapping rule:
      1. Concatenate company prefix and item reference to form GTIN-14.
      2. Preserve required numeric padding.
      3. Map EPC serial component to AI 21.
      4. Reverse mapping is possible where components are present and
         unambiguous.

   No EPC URN and GS1 URN are lexically equivalent solely because a
   mapping exists between them.
